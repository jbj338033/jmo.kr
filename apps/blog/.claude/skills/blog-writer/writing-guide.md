## 핵심 철학

### 3가지 핵심 가치

#### 1. 친근하면서도 전문적
- 존댓말이지만 격식 없이
- 기술적이지만 쉽게 설명
- 전문가지만 공감 가능하게

```markdown
❌ "본 연구에서는 AI 기술의 발전이 소프트웨어 개발 패러다임에 미치는 영향을 분석하였다."
✅ "저도 이런 질문을 자주 받았어요. AI가 개발자를 대체할까요?"
```

#### 2. 데이터로 증명, 추상적 주장 지양
- "좋다"가 아니라 "클릭률이 10배 올랐어요"
- "효과적이다"가 아니라 "전환율이 4배 높았어요"
- 숫자와 실제 사례로 뒷받침

#### 3. 독자 중심 구조
- 읽는 사람이 길을 잃지 않도록
- 명확한 흐름: 배경 → 문제 → 해결 → 인사이트
- 예측 가능한 구조

## 문체와 톤

### 1. 존댓말 스타일

#### 사용하는 존댓말
```
✅ ~해요 / ~했어요 / ~할게요
✅ ~해줘요 / ~되어요
✅ ~할까요? / ~있어요
```

#### 피하는 존댓말
```
❌ ~합니다 / ~하였습니다
❌ ~이다 / ~인 것이다
❌ ~하겠습니다 / ~할 것입니다
```

#### 실제 예시
```markdown
# 딱딱함 (X)
"본 연구에서는 마케팅 문구의 효과를 측정하기 위해 A/B 테스트를 수행하였습니다."

# toss.tech 스타일 (O)
"이렇게 제약이 많은데 어떻게 성과를 낼 수 있을까요? 저도 이런 질문을 자주 받았어요."
```

### 2. 개인적 경험 공유

#### 작성자 신원 명확히
```markdown
# 글 시작 패턴
안녕하세요, 토스 [직무] [이름]입니다.
```

예시:
- "안녕하세요, 토스 Node.js Developer 정세훈입니다."
- "저는 토스에서 UX 라이터로 일하고 있어요."

#### 개인적 느낌 포함
```markdown
❌ "개발자들은 이런 문제를 겪는다"
✅ "저도 이런 질문을 자주 받았어요"
✅ "처음에는 당연히 혜택에 눈이 갈 거라고 생각했어요"
```

### 3. 대화체 특징

#### 질문으로 독자 참여 유도
```markdown
- "그렇다면 무엇이 대체되고, 무엇이 남을까요?"
- "대체 뭘 써요?"
- "같은 행동이라도, 어떤 단어를 쓰느냐에 따라 느껴지는 무게가 달라져요."
```

#### 친근한 구어체
```markdown
✅ 작살내고
✅ ~썰
✅ ~죠 / ~니까 / ~잖아요
✅ 꿀팁
✅ ㅈㄷ (댓글에서)
```

## 글의 구조

### 1. 3단 구조 (필수)

```markdown
## [배경/도입]
왜 이 주제를 다루는가?
어떤 맥락에서 시작되었는가?

## [본론 - 번호 매긴 섹션]
1. 첫 번째 원칙/개념
2. 두 번째 원칙/개념
3. 세 번째 원칙/개념
...

## [맺으며]
핵심 메시지 정리
독자에게 남기고 싶은 말
```

### 2. 도입부 작성법

#### 좋은 도입부의 3요소
1. **작성자 소개**: "안녕하세요, [직무] [이름]입니다"
2. **문제 제기**: 독자가 공감할 수 있는 질문이나 상황
3. **글의 목적**: 이 글에서 무엇을 다룰 것인가

#### 실제 예시

```markdown
# 예시 1: 마케팅 문구 글
안녕하세요, UX 라이터 유아란입니다.

토스는 사용자를 속이지 않는 문구를 쓰기 위한 여러가지 원칙들이 있어요.
클릭을 유도하기 위해 과장하거나 불안을 자극하지 않고, 모두가 이해할 수 있는
말로만 쓰죠.

"그럼 대체 뭘 써요?"

이렇게 제약이 많은데 어떻게 성과를 낼 수 있을까요? 저도 이런 질문을 자주
받았어요. 답을 찾기 위해 수 십개의 서비스에서 수백 번의 문구 테스트를
돌렸고, 사용자가 반응하는 문구의 패턴을 조금씩 찾아냈어요.
```

```markdown
# 예시 2: 기술 에세이
안녕하세요, 토스 Node.js Developer 정세훈입니다.

요즘 너무나 많은 분들이 고민하고, 토론하고 계신 주제가 바로
'개발자는 과연 AI에게 대체될 것인가?'라는 질문이죠. 아무도 이 질문에
쉽게 대답하진 못하지만, 개발자로서 마냥 모른척 하기도 어렵습니다.

저의 개인적인 생각이니 가볍게 읽어주시길 바라며, 댓글로 여러분의 생각을
공유해 주시면 더 좋을 것 같습니다.
```

### 3. 본론 구조화

#### 번호 매긴 섹션 (필수)
```markdown
## 1. 첫 번째 원칙
### 1) 구체적 사례 A
### 2) 구체적 사례 B

---

## 2. 두 번째 원칙
### 1) 구체적 사례 A
### 2) 구체적 사례 B
```

#### 섹션 간 구분선
```markdown
---
또는
***
또는
separator (시각적 구분)
```

### 4. 마무리 작성법

#### 좋은 마무리의 특징
1. **핵심 메시지 재강조**
2. **독자에게 남기는 말**
3. **행동 유도 (optional)**

#### 실제 예시

```markdown
# 예시 1: 실용 가이드
마케팅 문구는 어떤 가치를 전달할 것이냐 뿐만 아니라 어떤 표현을 쓸 것이냐도
매우 중요하죠. 단어 하나에 따라서 클릭률과 전환율이 달라지기도 하니까요.

어떤 표현을 써야 할지 고민되는 순간에, 이 글이 자그마한 도움이 되었으면
좋겠어요. 마케팅 문구를 작성해야 할 때, 아래 원칙들을 하나씩 떠올리며
아이디어를 떠올려보세요.

1. 단 하나의 핵심만 전달하기
2. 확실한 보상 약속하기
...
```

```markdown
# 예시 2: 철학적 에세이
AI가 전문성의 종말을 초래할까요?

아닙니다. 직업은 자동화할 수 있는 하나의 업무가 아니라, 여전히 사람의
손길과 판단이 필요한 복잡한 업무들의 집합으로 이루어져 있습니다.

우리는 어떤 부분을 AI에게 위임하고, 어떤 부분에 우리의 전문성을 집중할지
선택해야 합니다. 그 선택을 위한 능력을 키우는 것이, 지금 우리가 해야 할
가장 중요한 일입니다.
```

## 문장 작법

### 1. 짧고 명확한 문장

#### 한 문장 = 한 아이디어
```markdown
❌ "이러한 상황에서 우리는 복잡한 의사결정 과정을 거쳐야 하며,
   이는 시간이 오래 걸리고 비효율적일 수 있습니다."

✅ "우리는 선택해야 합니다."
```

#### 문장 길이 권장
- 짧은 문장: 10~20자
- 보통 문장: 30~50자
- 긴 문장: 60자 이하

```markdown
# 리듬감 있는 문장 배치
짧은 문장.
조금 더 긴 문장으로 설명을 추가해요.
그리고 이렇게 다시 중간 길이로 전환합니다.
```

### 2. 강력한 동사 사용

#### 생생한 동사 선택
```markdown
❌ "문제를 해결했다"
✅ "작살냈다" / "찾아냈어요" / "뽑아냈어요"

❌ "변경했다"
✅ "바꿨어요" / "고쳤어요" / "뜯어고쳤어요"

❌ "개선했다"
✅ "끌어올렸어요" / "높였어요"
```

### 3. 구체적인 표현

#### 추상 → 구체
```markdown
❌ "많이 증가했습니다"
✅ "10배 올랐어요"

❌ "효과가 있었습니다"
✅ "클릭률이 6배 높아졌어요"

❌ "빠르게"
✅ "3분 만에" / "순식간에"
```

### 4. 비유와 은유

#### 복잡한 개념을 익숙한 것으로
```markdown
# 좋은 비유 예시
- "추상화는 복잡성을 미래로 이동시키는 것입니다"
- "AI 혁명은 1995년 인터넷의 전화 접속 단계"
- "Harness는 원래 '마구(馬具)'를 뜻합니다"
- "MCP = Infrastructure / Adapter"
```

#### 비유 활용 패턴
```markdown
[복잡한 기술 개념] = [일상적 비유]

예시:
- Context Window = 작업 메모리
- 토큰 사용량 = 메모리 점유율
- Slash Command = Controller
```

### 5. 강조 기법

#### 문장 끝에 중요한 말
```markdown
❌ "저는 이 방법이 가장 중요하다고 생각해요."
✅ "가장 중요한 건, 이 방법입니다."
```

#### 짧은 문장으로 포인트
```markdown
"버블입니다."
"그런데 잠깐."
"핵심은 지향입니다."
"결국 본질적인 구분은 하나 뿐입니다."
```

## 콘텐츠 전략

### 1. Before/After 패턴

#### Winner/Loser 비교 (마케팅/디자인 글)
```markdown
### Loser
`소비 궁합` 알아보고 `신혼부부 지원금` 받기

### Winner
`커플 유형 테스트` 도착 문제 10개 찍고 결과 보기

→ 결과: 노출 수와 클릭률이 10배 이상 높음
```

#### 잘못된 접근 vs 올바른 접근
```markdown
❌ "AI를 사용해서 이만큼 빨리 했으니, 더 많은 일을 맡을 수 있겠다"

✅ "AI로 빨리 했으니 경계를 다듬고 더 많은 일들을 위임하자"
```

### 2. 데이터 제시 방법

#### 구체적 수치
```markdown
- "클릭률이 10배 이상 높게 나왔어요"
- "전환율이 4배 올랐어요"
- "노출이 20배나 더 잘됐죠"
- "Magnificent 7이 2년간 5,600억 달러를 쏟아 부었습니다"
```

#### 비율과 비교
```markdown
- "16:1의 불균형입니다"
- "95%의 도입이 실패했고"
- "77%는 내부거래입니다"
```

### 3. 예시 코드 스타일

#### 간단하고 읽기 쉽게
```javascript
// ❌ 너무 복잡한 예시
class UserAuthenticationServiceWithValidationAndLogging {
  async authenticateUserWithMultipleSteps() { ... }
}

// ✅ 핵심만 보여주기
function isPrime(n) {
  if (n <= 1) return false
  for (let i = 2; i * i <= n; i++) {
    if (n % i === 0) return false
  }
  return true
}
```

#### 주석으로 설명 추가
```javascript
// 안티패턴: LLM이 컨벤션을 매번 해석
"브랜치명은 feature/JIRA-{티켓번호}-{설명} 형식으로..."

// 권장: scripts가 컨벤션을 캡슐화
./scripts/create-branch.sh JIRA-1234 "로그인 기능"
→ feature/JIRA-1234-login-feature
```

### 4. 표(Table) 활용

#### 비교 표
```markdown
| 전통 방식 | HITL 방식 |
|---|---|
| 모든 케이스를 미리 정의해야 함 | 애매하면 물어보면 됨 |
| 예외 상황 → 에러 또는 기본값 | 예외 상황 → 사용자 판단 요청 |
| 자동화 100% 아니면 0% | 부분 자동화 가능 |
```

#### 정리 표
```markdown
| LLM 한계 | Harness 역할 |
|---|---|
| Context window 제한 | Memory 관리 |
| 환각(Hallucination) | Fact grounding, RAG |
| 도메인 지식 부족 | Knowledge Base |
```

## 시각적 구조

### 1. 제목 계층

```markdown
# H1: 글 제목 (한 번만)
소프트웨어 3.0 시대를 맞이하며

## H2: 대제목 (메인 섹션)
Harness: LLM을 쓸모있게 만드는 것

### H3: 중제목 (서브 섹션)
각 레이어를 자세히 보면

#### H4: 소제목 (거의 사용 안 함)
```

### 2. 강조 요소

#### 코드 블록으로 핵심 강조
```markdown
`단일 책임` 원칙에 따라 `하나의 역할`만 담당해야 합니다.
```

#### 인용문으로 중요 메시지
```markdown
> "기술의 효과는 단기적으로 과대평가되고, 장기적으로 과소평가되는 경향이 있다."
```

#### 구분선
```markdown
---
(섹션 간 명확한 구분)
```

### 3. 리스트 활용

#### 불릿 리스트
```markdown
버릴 것:
• "모든 로직을 명시적으로 작성해야 한다"는 강박
• 모든 예외 상황을 미리 정의하려는 시도
• LLM을 '똑똑한 자동완성' 정도로만 보는 시각
```

#### 번호 리스트
```markdown
1. 단 하나의 핵심만 전달하기
2. 확실한 보상 약속하기
3. 행동을 가볍게 표현하기
```

### 4. 박스/강조 섹션

```markdown
### 질문해야 할 때:
• 되돌리기 어려운 작업 (삭제, 배포, 외부 API 호출)
• 여러 선택지가 있고 정답이 없는 경우
• 비용이나 리스크가 큰 결정
```

## 카테고리별 특징

### Engineering 글

#### 특징
- **길이**: 5,000자 이상 (긴 호흡)
- **깊이**: 철학적 질문, 개념 탐구
- **스타일**: 에세이 + 기술 해설
- **구조**: 문제 제기 → 분석 → 인사이트 → 마무리

#### 전형적인 흐름
```markdown
1. 도입 - 큰 질문 던지기
   "개발자는 AI에게 대체될 것인가?"

2. 배경/현상 분석
   "우리는 버블을 보고 있습니다"

3. 깊이 있는 분석
   "질문을 바꿔야 합니다"
   "위임의 4분면"
   "추상화는 미래에 대한 예측입니다"

4. 실천 방향 제시
   "우리가 해야 할 것"

5. 마무리
   핵심 메시지 + 독자에게 남기는 말
```

#### 표현 특징
```markdown
- 철학적 질문: "그렇다면 ~일까요?"
- 개념 정의: "~란 무엇인가"
- 비유 활용: "마치 ~처럼"
- 참고문헌 명시
```

### Design 글

#### 특징
- **길이**: 2,000~3,000자 (중간)
- **깊이**: 실용적 팁과 가이드
- **스타일**: 하우투 + 사례 중심
- **구조**: 배경 → 원칙 나열 → 사례 → 정리

#### 전형적인 흐름
```markdown
1. 배경 설명
   "토스는 사용자를 속이지 않는 문구를 씁니다"

2. 번호 매긴 원칙들
   "1. 단 하나의 핵심만 전달하기"
   "2. 확실한 보상 약속하기"
   ...

3. 각 원칙마다:
   - 설명
   - Before/After (Winner/Loser)
   - 결과 수치

4. 마무리
   원칙 요약 + 적용 권장
```

#### 표현 특징
```markdown
- Winner/Loser 비교
- 구체적 수치 (클릭률, 전환율)
- "~해보세요" 행동 유도
- 실전 팁
```

### Product 글

#### 특징
- **길이**: 3,000~4,000자
- **깊이**: 문제 해결 과정
- **스타일**: 스토리텔링 + 인사이트
- **구조**: 문제 → 시도 → 해결 → 배움

## 실전 체크리스트

### 글 작성 전

```markdown
□ 작성자 신원 명확히 (이름, 직무)
□ 독자가 공감할 문제/질문 정의
□ 글의 목적과 범위 설정
□ 카테고리 결정 (Engineering/Design/Product)
```

### 도입부

```markdown
□ "안녕하세요, [직무] [이름]입니다" 형식
□ 독자가 공감할 상황/질문 제시
□ 개인적 경험 언급
□ 글에서 다룰 내용 예고
```

### 본론 작성 시

```markdown
□ 번호 매긴 섹션 사용 (1, 2, 3...)
□ 각 섹션에 명확한 제목
□ 섹션 간 구분선 (---)
□ 추상적 설명 → 구체적 예시 순서
□ Before/After 비교 (해당시)
□ 데이터/수치 제시
□ 코드 예시는 간단명료하게
□ 복잡한 개념은 비유 활용
```

### 문장 스타일

```markdown
□ ~해요/~했어요 존댓말
□ 짧고 명확한 문장
□ 생생한 동사 사용
□ 구체적인 표현 (숫자, 예시)
□ 질문으로 독자 참여 유도
□ 친근한 구어체 (적절히)
```

### 시각적 요소

```markdown
□ 제목 계층 명확히 (H2, H3)
□ 강조 요소 활용 (`코드`, **볼드**)
□ 인용문으로 핵심 메시지
□ 리스트로 정리
□ 표로 비교/정리
□ 이미지/다이어그램 (필요시)
```

### 마무리

```markdown
□ 핵심 메시지 재강조
□ 독자에게 남기는 말
□ 행동 유도 (optional)
□ 참고자료 명시 (Engineering 글)
```

### 최종 검토

```markdown
□ 전체 흐름이 자연스러운가?
□ 각 섹션이 독립적으로도 이해되는가?
□ 데이터/사례가 충분한가?
□ 독자가 실제로 적용 가능한가?
□ 불필요한 전문용어는 없는가?
□ 문장이 너무 길지 않은가?
```

## 자주 하는 실수

### 1. 독자를 고려하지 않은 전문성
```markdown
❌ "레이턴시 p99가 200ms에서 50ms로 개선되었고 throughput이 2배 향상"
✅ "응답 속도가 4배 빨라졌어요. 사용자가 기다리는 시간이 확 줄어든 거죠."
```

### 2. 추상적인 설명
```markdown
❌ "성능이 크게 개선되었습니다"
✅ "API 응답 시간이 2초에서 0.5초로 줄었어요"
```

### 3. 구조 없는 나열
```markdown
❌ 한 단락에 여러 개념을 섞어서 설명
✅ 하나의 개념 = 하나의 섹션
```

### 4. 결론 없는 끝
```markdown
❌ 갑자기 끝남, 또는 "이상입니다"
✅ 핵심 메시지 재강조 + 독자에게 남기는 말
```
